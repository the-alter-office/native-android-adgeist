# AdGeist Android Ad Serving SDK — Code Review

**Scope reviewed:** `adgeistkit` module (public SDK: `AdgeistCore`, `ads/*`, `core/*`, `data/*`, `request/*`), its manifest, Gradle build config, ProGuard/consumer rules, and the `app` example module + READMEs. Version at time of review: `1.1.29-beta` (gradle.properties), AGP 8.9.0, Kotlin 1.8.0, compileSdk 35, minSdk 23.

Priority scale: **Critical** (can crash/leak data in production or blocks compliance) → **High** (real user/publisher impact, fix soon) → **Medium** (should fix, not urgent) → **Low** (polish/nice-to-have).

---

## 1. Performance (GC, memory, threads, data updates/loss)

| Name | What is there in current version | What needs to be done | Reason and sources | How can it be implemented | Priority |
|---|---|---|---|---|---|
| ✅ **Done** — New OkHttpClient per request path | `FetchCreative.fetchCreative()` (`data/network/FetchCreative.kt:104`) instantiates `OkHttpClient()` on every call, and `CreativeAnalytics` (`data/network/CreativeAnalytics.kt:20`) instantiates a fresh one per `CreativeAnalytics` object, itself created new on every `AdgeistCore.getCreative()`/`postCreativeAnalytics()` call (`AdgeistCore.kt:142-148`). | Share a single, lazily-built `OkHttpClient` (with a bounded connection pool and explicit timeouts) across all SDK network calls. | Each `OkHttpClient()` spins up its own dispatcher thread pool and connection pool; creating one per ad/impression/click means the SDK spawns and discards thread pools continuously on apps with many ad slots (feeds), causing avoidable GC pressure and socket/thread churn. No `connectTimeout`/`readTimeout` is set either, so a stalled request can hold resources for the OkHttp default (10s) per call. | Add a `companion object` singleton `OkHttpClient` in `AdgeistCore` (or a small `NetworkModule`) built once with `connectTimeout`, `readTimeout`, and a `Dispatcher` with a sane `maxRequestsPerHost`; inject it into `FetchCreative`/`CreativeAnalytics` instead of `OkHttpClient()`. | High |
| ✅ **Done** — Unstructured, uncancellable coroutine scopes | `CoroutineScope(Dispatchers.IO)` / `CoroutineScope(Dispatchers.Main)` are created ad hoc in `AdgeistCore.logEvent()`, `CreativeAnalytics.sendTrackingDataV2()`, and `FetchCreative` (`scope` field), with no `Job`/`SupervisorJob` reference kept and never cancelled. | Use a single lifecycle-scoped `CoroutineScope(SupervisorJob() + Dispatchers.IO)` owned by `AdgeistCore`, cancelled in `AdgeistCore.destroy()`; stop creating a new scope per call/object. | Coroutines launched this way have no owner to cancel them — if a WebView/AdView is destroyed mid-request the coroutine keeps running (wasted CPU/network) and the object holding it (and everything it closes over, e.g. `Context`) cannot be GC'd until the coroutine completes. | Add `private val ioScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)` to `AdgeistCore`, expose it (or a launch helper) to `FetchCreative`/`CreativeAnalytics`, cancel it in `destroy()`. | High |
| `logEvent()` drops every event (data loss) | `AdgeistCore.logEvent()` (`AdgeistCore.kt:150-161`) builds `fullEvent` inside a coroutine and then never sends it anywhere — no network call, no queue, no return value. | Either wire `logEvent` to an actual analytics endpoint (batched, like `CreativeAnalytics`) or remove/mark the API `@Deprecated` until implemented. | This is a public method a publisher can call believing events are tracked; today it is a complete no-op, silently discarding 100% of custom event data. This is the most direct "inefficient data update / data loss" finding in the codebase. | Implement `sendCustomEvent(fullEvent)` via the shared OkHttp client to a `/v2/ssp/event` (or similar) endpoint, mirroring `CreativeAnalytics.sendTrackingDataV2`; add a unit test asserting a network call is made. | Critical |
| `AdSessionStore` retains WebView/Activity refs indefinitely | `AdSessionStore` (`ads/AdSessionStore.kt`) is a singleton `object` holding `AdSession` entries with strong references to `webView`, `hostActivity`, and `hostView` (`ads/AdSessionStore.kt:11-20`); entries are only removed via explicit `destroy()`/`removeIfHosts()` paths. | Add a safety net: either a `WeakReference` to `hostActivity`, or a periodic/`onTrimMemory`-triggered sweep that drops sessions whose `hostActivity` is `isFinishing/isDestroyed`, so a missed teardown path can't pin an Activity+WebView for the process lifetime. | Static/singleton fields holding `Activity` or `View` references are a classic Android memory-leak pattern; if any exception or unusual navigation path skips `destroy()`/`safelyDestroyWebView()`, the session (and its Activity) is leaked until the process dies. | Wrap `hostActivity` in `WeakReference<Activity>`; in `BaseAdView.registerHostDestroyWatcher`'s `onDestroy` callback (already firing) call `AdSessionStore.remove` defensively even when the view itself no-ops. | Medium |
| `clearCache(true)` wipes the app's global WebView cache | `BaseAdView.safelyDestroyWebView()` calls `webViewToDestroy.clearCache(true)` (`ads/BaseAdView.kt:786`). | Use `clearCache(false)` (clears only in-memory cache) or drop the call entirely; do not clear the on-disk WebView cache shared by the whole app. | `WebView.clearCache(true)` clears the **shared, app-wide** WebView disk cache database, not just this instance's data. An ad SDK tearing down one ad view can unexpectedly blow away cached resources for any other WebView the host app uses, hurting the app's own performance. | Change the boolean argument to `false`, or remove the call since `destroy()`/`loadUrl("about:blank")` already release the render tree. | Medium |
| Fresh `Gson()` allocated repeatedly | `Gson()` is instantiated inline in `BaseAdView.renderAdWithAdCard` and multiple times in `FetchCreative` (`FetchCreative.kt:122,171`) instead of being reused. | Hold one `Gson` instance (e.g. a top-level `private val gson = Gson()` per class or a shared singleton) and reuse it. | `Gson()` construction is not free (reflection caches, adapter factories set up each time); repeated allocation on the hot ad-load/analytics path adds avoidable GC churn. | Add a companion-object `Gson` instance per class, or one shared instance passed via constructor. | Low |
| Verbose logging left enabled in release builds | Nearly every class (`BaseAdView`, `AdActivity`, `FetchCreative`, `JsBridge`, etc.) calls `Log.d/Log.i` unconditionally, including per-frame `onMeasure` logs (`ads/BaseAdView.kt:567,570`). | Gate non-error logs behind `BuildConfig.DEBUG` or a configurable SDK log level. | String concatenation/formatting for `Log.d` calls still executes in release builds since Android doesn't strip log calls by default; on a view that logs from `onMeasure`/`onLayout`, this adds needless allocation on every layout pass. (Also a security/disclosure concern — see Security table.) | Add a tiny `AdgeistLog` wrapper that no-ops `d/i` calls when `!BuildConfig.DEBUG`, and route all internal logging through it. | Medium |

## 2. Crash surface area

| Name | What is there in current version | What needs to be done | Reason and sources | How can it be implemented | Priority |
|---|---|---|---|---|---|
| `adSize!!` NPE when publisher forgets `setAdDimension()` | In `BaseAdView.startAdLoad`'s response callback, non-responsive ads read `adSize!!.width` / `adSize!!.height` (`ads/BaseAdView.kt:358-359`) with no null check. | Validate `adSize` before use; if null and not responsive, fail gracefully via `listener?.onAdFailedToLoad(...)` instead of force-unwrapping. | If a publisher creates an `AdView`, sets `adUnitId`/`adType` but forgets `setAdDimension()` (and doesn't set `adIsResponsive = true`), this line throws a `NullPointerException` **inside the SDK's own callback**, crashing the host app — directly contradicting the "must never crash the publisher app" requirement. | `val size = adSize; if (size == null) { listener?.onAdFailedToLoad("adSize not set..."); return@post }` before building `propertiesForAdCard`. | Critical |
| Unstructured coroutines can crash the host app on any thrown exception | Coroutine bodies in `AdgeistCore.logEvent`, `CreativeAnalytics.sendTrackingDataV2`, and the pre-network setup in `FetchCreative.fetchCreative` (device/network lookups, request building) are not wrapped in `try/catch`, and the enclosing `CoroutineScope` has no `CoroutineExceptionHandler`/`SupervisorJob`. | Wrap coroutine bodies in `try/catch` (as `startAdLoad`'s outer function already does) and/or install a `CoroutineExceptionHandler` on the shared scope that logs instead of propagating. | An uncaught exception in a coroutine launched this way propagates to the dispatcher's thread and triggers the JVM's default uncaught-exception handling — i.e. it **crashes the app**, exactly the failure mode this SDK must avoid. This is a bigger risk than typical try/catch omissions because it bypasses normal call-stack exception handling entirely. | Add `CoroutineExceptionHandler { _, e -> Log.e(TAG, "...", e) }` to the shared `ioScope`/`mainScope`; also wrap risky calls (`toRequestBody`, JSON building, `Uri.parse`) explicitly. | Critical |
| `AdgeistCore.initialize()` throws on any `Throwable` | `initialize()` catches `Throwable` and rethrows a new `IllegalStateException` (`AdgeistCore.kt:58-61`), and the README's quick-start snippet calls it with no `try/catch`. | Either (a) make `initialize()` fail soft (log and return a degraded instance / null) so a single bad OEM API call can't take down the host app on launch, or (b) if throwing is intentional, update the README/Javadoc to explicitly instruct wrapping the call in `try/catch`. | Publishers copy-pasting the documented quick start get zero exception handling around SDK init; any unexpected `Throwable` from `SharedPreferences`, `PackageManager`, or `UiModeManager` inside the constructor chain crashes app startup. | Prefer soft-fail: return a "disabled" `AdgeistCore` singleton on failure so ad calls simply no-op/fail gracefully instead of preventing app start. | High |
| Pervasive `!!` (force non-null) usage | `BaseAdView`/`JsBridge`/`AdActivity` use `!!` extensively (e.g. `webView!!`, `jsInterface!!`, `session.webView!!`) rather than safe calls or explicit guards. | Replace `!!` with `?.let{}`/early-return guards throughout the ad-loading and teardown paths. | Every `!!` is a latent `NullPointerException`; while most mutations happen on the main thread and are currently sequenced safely, this pattern is fragile — a future refactor or an unexpected re-entrant call (e.g. `destroy()` invoked from a callback while another callback is mid-execution) can turn a null field into a crash. | Systematic pass replacing `!!` with null-safe alternatives; add lint rule (`ktlint`/detekt "no-unsafe-call") to prevent regressions. | High |

## 3. Code quality (readability, maintainability)

| Name | What is there in current version | What needs to be done | Reason and sources | How can it be implemented | Priority |
|---|---|---|---|---|---|
| Dead / non-functional public API left in place | `logEvent()` (no-op, see Performance table), `NetworkUtils.isNetworkAvailable()` (never called anywhere in the SDK), and `consentGiven` (stored but never read to gate anything) are shipped as if functional. | Either finish the implementation or remove/`@Deprecated` these members so the public API surface reflects what actually works. | Confirmed via repo-wide grep: `isNetworkAvailable` has zero call sites, `consentGiven`/`getConsentStatus()` are never checked before collecting device data, `logEvent` never transmits. Leaving them in place misleads integrators and future maintainers about SDK behavior. | Remove unused methods or wire them up (consent enforcement should go into Security fixes below); document any intentionally-unused-for-now API as `@Deprecated("Not yet implemented")`. | High |
| Redundant self-lookup via companion `getInstance()` | `AdgeistCore.getCreative()` and `postCreativeAnalytics()` call `AdgeistCore.getInstance()` (`AdgeistCore.kt:142-148`) from inside an *instance* method instead of using `this`. | Replace `AdgeistCore.getInstance()` with `this` inside instance methods. | If `destroy()`+`initialize()` (SDK re-configuration, exactly what `HomeFragment.configureSDK()` in the example app does) happens between a caller obtaining an `AdgeistCore` reference and calling `getCreative()`, the method silently returns wiring for a *different* (the new current) singleton instance than the one the caller holds — confusing behavior, and `getInstance()` can also throw `IllegalStateException` unexpectedly if called mid-reconfiguration. | One-line fix: `FetchCreative(this)` / `CreativeAnalytics(this)`. | Medium |
| Auto-generated-looking parameter name in public API | `AdListener.onAdFailedToLoad(var1: String)` (`ads/AdListener.kt:10`) uses `var1` instead of a descriptive name like `errorMessage`. | Rename the parameter to something descriptive (e.g. `errorMessage`); Kotlin named-parameter overrides will surface the better name to callers. | Public callback parameter names are part of the developer-facing API/IDE autocomplete experience; `var1` looks like a decompiled/copy-pasted stub and hurts both readability and integrator trust. | Simple rename in `AdListener.kt`; no ABI break since Kotlin open functions don't encode parameter names in the JVM signature. | Low |
| String-typed protocol between JS and native, no constants | Values like `"video"`, `"FIXED"`, `"RENDER_STATUS"`, `"Success"`, `"PLAY"/"PAUSE"/"ENDED"` are compared as raw string literals across `BaseAdView`, `AdActivity`, `JsBridge`, and `FetchCreative`. | Extract these into shared `const val`/sealed types (e.g. an internal `object JsMessageType`) used on both the Kotlin side and referenced by name in the JS assets. | Typos in either the native or JS side silently break tracking/rendering with no compiler check and no runtime error — e.g. mistyping `"PLAY"` in `adcard-beta.js` would silently stop video-play tracking. | Add an internal `object AdBridgeProtocol { const val TYPE_PLAY = "PLAY"; ... }`; reference from Kotlin, and keep the JS asset's literals in sync via a comment pointing at the Kotlin source of truth. | Medium |
| Minimal test coverage on core SDK logic | `adgeistkit`'s own `test`/`androidTest` source sets contain only the default template tests (`ExampleUnitTest.kt`, `ExampleInstrumentedTest.kt`); real coverage (`AdModelR8Test`, `JavaInteropSmokeTest`) lives in the **example app**, and only covers Gson/R8 keep-rules and Java-callable `initialize()`. | Add unit tests inside `adgeistkit` for `AdActivity` viewability math (`checkVisibility`, `scrollDepth`), `BaseAdView` session-adoption logic, and `FetchCreative`/`CreativeAnalytics` request building/parsing (using MockWebView/OkHttp `MockWebServer`). | The riskiest logic in the SDK (session survival across navigation, viewability thresholds, R8-sensitive parsing) has no direct unit tests co-located with the code that implements it; regressions can only be caught by the example app's much narrower smoke tests. | Add `androidx.test`/`mockwebserver`/`robolectric` test deps to `adgeistkit/build.gradle.kts`; write targeted tests per class. | Medium |
| No CI gate for tests/lint on pull requests | The only workflow (`.github/workflows/artifact-release.yaml`) runs on push to `main`/`qa` and publishes artifacts; there is no CI job running unit/instrumented tests or lint on PRs. | Add a `pr-check.yaml` workflow that runs `./gradlew :adgeistkit:test :app:testBetaDebugUnitTest lint` (and ideally the R8 instrumented test) on every PR. | Without a test-and-lint gate, regressions (including the R8 keep-rule regression `AdModelR8Test` exists specifically to catch) can merge to `main`/`qa` and only surface after a real publish. | Standard GitHub Actions workflow triggered on `pull_request`, reusing the JDK 17 setup from the existing release workflow. | Medium |
| Duplicate `DeviceMeta` construction | `TargetingOptions.getTargetingInfo()` constructs its own `DeviceMeta(context)` (`core/TargetingOptions.kt:10`) instead of reusing the `deviceMeta` instance `AdgeistCore` already created (`AdgeistCore.kt:99`). | Pass the existing `DeviceMeta` instance into `TargetingOptions` instead of constructing a second one. | Minor DRY violation; not harmful today since `DeviceMeta` is cheap/stateless, but it's an easy inconsistency to propagate if `DeviceMeta` ever gains state or caching. | Change `TargetingOptions(context: Context)` to `TargetingOptions(deviceMeta: DeviceMeta)` and pass `this.deviceMeta` from `AdgeistCore.init`. | Low |

## 4. Security (access control, method/class visibility)

| Name | What is there in current version | What needs to be done | Reason and sources | How can it be implemented | Priority |
|---|---|---|---|---|---|
| Consent flag is stored but never enforced | `AdgeistCore.updateConsentStatus()`/`getConsentStatus()` persist a boolean to `SharedPreferences` (`AdgeistCore.kt:133-140`), but **no code path checks it** before collecting the Advertising ID (`DeviceIdentifier`), full device fingerprint (`DeviceMeta.getAllDeviceInfo()` — brand, screen, OS, NFC/VR/GPU capability, network operator, etc.), local/WiFi IP (`NetworkUtils`), or before sending analytics (`CreativeAnalytics`) / fetching ads. | Gate all data-collection and network calls on `getConsentStatus()` (or a more granular consent model, e.g. per-purpose) before `DeviceIdentifier`/`DeviceMeta`/`NetworkUtils` are invoked; default to a privacy-safe (non-personalized / minimal-collection) path when consent is false or unset. | An ad SDK that collects advertising ID + device fingerprint + IP regardless of a consent flag it itself exposes is a serious compliance gap under GDPR/CCPA and Google Play's User Data policies — the API *implies* consent is respected when it currently has zero effect. This is the most significant finding in the whole review given the stated adtech/compliance context. | In `AdgeistCore.init`/`getCreative()`/`postCreativeAnalytics()`, check `consentGiven` (or a `ConsentMode` enum) and short-circuit device-fingerprint collection / substitute a coarser payload when consent is withheld; add a unit test asserting no device data is sent when consent is false. | Critical |
| `READ_PHONE_STATE` requested for network type only | The SDK requests the dangerous `android.permission.READ_PHONE_STATE` permission (`adgeistkit/src/main/AndroidManifest.xml:6`) solely to read `TelephonyManager.dataNetworkType`/`networkOperatorName` (`DeviceMeta.kt:82-133`). | Drop the permission requirement; approximate network class from `ConnectivityManager`/`NetworkCapabilities` transport type (WIFI/CELLULAR/ETHERNET), which needs no dangerous permission, or make the whole network-type signal opt-in via an explicit publisher call. | `READ_PHONE_STATE` is flagged prominently in Google Play's Data Safety form, is disallowed for apps in the Families/Kids program, and often triggers extra Play Console review — a heavy cost for a "nice to have" targeting signal, and it also *requires* every publisher to justify a dangerous permission that's really the SDK's, not the app's. | Remove the permission from the SDK manifest and the `READ_PHONE_STATE`-gated code paths in `DeviceMeta`; if precise carrier network generation is still wanted, request it as a publisher-opt-in flag documented clearly as "requires READ_PHONE_STATE". | High |
| WebView remote debugging enabled unconditionally | `BaseAdView.renderAdWithAdCard()` calls `WebView.setWebContentsDebuggingEnabled(true)` unconditionally for API 19+ (`ads/BaseAdView.kt:416-418`), including prod/release builds. | Gate behind `BuildConfig.DEBUG` (or a publisher-supplied debug flag), so production builds ship with debugging disabled. | With debugging enabled, anyone with local `adb` access (or a malicious app abusing a rooted/ADB-over-network setup) can inspect and script the ad WebView via `chrome://inspect`, including calling the exposed `@JavascriptInterface` bridge methods directly — an unnecessary attack surface in shipped apps. | `if (BuildConfig.DEBUG) WebView.setWebContentsDebuggingEnabled(true)` — note `BuildConfig` here must be the **library's** `BuildConfig`, or better, plumb a debug flag from `AdgeistCore.initialize()`. | High |
| Creative JSON injected into inline `<script>` without neutralizing `</script>` | `buildAdCardHtml()` escapes `\`, `"`, `\n`, `\r`, `\t`, and `` ` `` before embedding creative data inside `JSON.parse("{{CREATIVE_DATA}}")` in `ad_view.html` (`ads/BaseAdView.kt:510-528`), but does **not** neutralize `</script>` sequences. | Additionally escape `</script>` (e.g. replace with `<\/script>`) — and more robustly, pass the JSON via a `<script type="application/json">` element read by `JS`, or via `evaluateJavascript()` with a properly-encoded argument instead of raw string interpolation. | If any creative field (title/description/ctaUrl, which come from the ad server / advertiser-supplied content) contains the literal sequence `</script>`, it closes the surrounding `<script>` tag early and lets injected markup/script execute in the page — which has `javaScriptEnabled=true`, `domStorageEnabled=true`, and an `addJavascriptInterface("Android", ...)` bridge exposing `postMessage`/`postVideoStatus`/`reportOverflow`/`showAd`. This is a classic script-injection vector that specifically matters here because a compromised/malicious advertiser account, not just a compromised CDN, could exploit it. | Add `.replace("</script>", "<\\/script>")` (and `<!--`) to the existing `.replace(...)` chain; add a regression test with a title containing `</script><script>` confirming it renders as literal text. | High |
| Ad-click navigation opens arbitrary URLs via `Intent.ACTION_VIEW` with no scheme allow-list | `BaseAdView.openInBrowser()` (`ads/BaseAdView.kt:840-848`) does `Intent(Intent.ACTION_VIEW, Uri.parse(url))` for whatever URL the ad creative's `shouldOverrideUrlLoading` hands it, with no scheme validation. | Restrict to `http`/`https` schemes before constructing the intent; reject/no-op (and log) anything else. | A malicious or compromised creative's `ctaUrl` (or any link inside the rendered ad HTML) can use non-http schemes (`intent://`, custom app schemes, `market://`, etc.) to trigger unintended actions in other installed apps — the well-known "Android intent scheme" attack pattern — since the SDK forwards the URL to `ACTION_VIEW` unconditionally. | `if (uri.scheme in setOf("http","https")) startActivity(intent) else Log.w(TAG, "Blocked non-http(s) ad click URL: $url")`. | High |
| WebView not hardened against local file/content access | `renderAdWithAdCard()` sets `javaScriptEnabled`/`domStorageEnabled`/`loadWithOverviewMode`/`useWideViewPort` but never explicitly disables `setAllowFileAccess`, `setAllowContentAccess`, `setAllowFileAccessFromFileURLs`, `setAllowUniversalAccessFromFileURLs` (`ads/BaseAdView.kt:404-410`). | Explicitly set all four to `false` (defaults vary by API level; don't rely on platform defaults). | Combined with JS enabled + a JS bridge, leaving file/content access implicit is unnecessary attack surface for a WebView whose HTML content originates from a third-party ad response. | Add the four `settings.setAllow*(false)` calls next to the existing `settings.*` block in `renderAdWithAdCard()`. | Medium |
| Blanket `-keep` disables obfuscation for the whole SDK in every consumer | `adgeistkit/consumer-rules.pro` applies `-keep class com.adgeistkit.** { *; }` to every consuming app's R8 pass, with a `TODO` in the file itself acknowledging it's a stopgap. | Narrow the keep rule to just the Gson-mapped model classes (`data.models.**`) and the `@JavascriptInterface`-annotated bridge (`JsBridge`), letting R8 obfuscate the rest of the SDK's implementation classes as intended. | A blanket keep rule means the SDK's business logic (session-adoption algorithm, viewability thresholds, request-building, backend URLs/headers) ships fully readable/reverse-engineerable in every publisher's release APK — undermining whatever protection R8 minification is meant to provide, for the whole SDK rather than just the reflection-sensitive parts. | Split into targeted rules, e.g. `-keep class com.adgeistkit.data.models.** { *; }`, `-keepclassmembers class com.adgeistkit.ads.JsBridge { @android.webkit.JavascriptInterface <methods>; }`, plus the existing `Signature/Annotation/InnerClasses` + enum rules; re-run `AdModelR8Test` to confirm Gson still binds correctly. | Medium |
| Overly public mutable field on internal bridge class | `JsBridge.mContext` is a public `var Context` (`ads/JsBridge.kt:12`) on a class that is effectively SDK-internal wiring, not part of the intended public API. | Mark `JsBridge` `internal` (like `AdSession`/`AdSessionStore` already are) and make `mContext` `private`/constructor-only unless externally needed. | Exposing a mutable `Context` setter on a class instantiated by the SDK itself unnecessarily widens the public API and invites misuse (e.g. a consumer swapping the context to something inconsistent with the live WebView). | `internal class JsBridge(...)`; change `mContext` visibility, exposing only what `BaseAdView`'s adoption logic (`rebind`) actually needs. | Low |
| Advertising ID used without checking opt-out / limit-ad-tracking state | `DeviceIdentifier.getAdvertisingId()` (`core/device/DeviceIdentifier.kt`) returns whatever `AdvertisingIdClient` provides, including a zeroed ID when the user has limited ad tracking, with no check before forwarding it as `deviceId` in ad/analytics requests. | Check `AdvertisingIdInfo.isLimitAdTrackingEnabled` and either omit the ID or flag the request as non-personalized when tracking is limited. | Forwarding a device identifier upstream without respecting the user's own OS-level ad-tracking opt-out defeats the purpose of that setting and is inconsistent with Google Play policy expectations for identifiers. | Switch to `AdvertisingIdClient.getAdvertisingIdInfo(context)` (already used) and read `.isLimitAdTrackingEnabled` alongside `.id`; suppress/replace the ID when true. | Medium |

## 5. Compatibility (Java/Kotlin versions, SDK versions)

| Name | What is there in current version | What needs to be done | Reason and sources | How can it be implemented | Priority |
|---|---|---|---|---|---|
| Library compiled for JVM 17 while example/consumer apps commonly target 8–11 | `adgeistkit/build.gradle.kts` sets `sourceCompatibility/targetCompatibility = JavaVersion.VERSION_17` and `kotlinOptions.jvmTarget = "17"` (lines 54-60), while the bundled example `app` module itself uses Java/Kotlin **11** (`app/build.gradle.kts:52-58`). | Lower the library's `jvmTarget`/`compileOptions` to the lowest broadly-supported value the code actually needs (11, or even 8 if nothing 9+ is used) unless a JVM17-only API is genuinely required. | Many publisher projects — especially older or enterprise Android codebases — still build with JDK 8/11 toolchains. An AAR whose Kotlin metadata/class files target JVM 17 can force every consumer to raise their own toolchain just to compile against this SDK, which is a real integration blocker, not a theoretical one (the example app in this very repo already targets 11, one step below what the SDK requires). | Change `JavaVersion.VERSION_17` → `VERSION_11` (or `VERSION_1_8`) and `jvmTarget = "17"` → `"11"` in `adgeistkit/build.gradle.kts`; re-run the full test/lint matrix to confirm nothing in the SDK actually needs 17. | High |
| Kotlin toolchain pinned to a multi-year-old version | `implementation(platform("org.jetbrains.kotlin:kotlin-bom:1.8.0"))` is forced in both `adgeistkit` and `app` (Kotlin 1.8.0 released early 2023; current Kotlin is in the 2.0/2.1 series), alongside AGP 8.9.0 and Kotlin Gradle plugin `1.8.0` (`gradle/libs.versions.toml:3`). | Upgrade the Kotlin Gradle plugin/BOM to a current stable release (2.0.x/2.1.x) compatible with AGP 8.9, and re-test; at minimum, stop force-pinning the BOM and let the Kotlin Gradle plugin manage the version. | Because the AAR's published POM will include `implementation`-declared runtime deps (kotlin-stdlib, coroutines, OkHttp, Gson, play-services-ads-identifier) as transitive runtime dependencies, a consumer app resolves them alongside its own — an old forced BOM increases the odds of dependency-resolution surprises (Gradle picks the highest requested version by default, so a consumer on an older, *lower* pin of the same library can be silently bumped, or hit resolution conflicts if strict versions are used). Kotlin 1.8.0 also predates the K2 compiler and current Compose-compiler compatibility tables, which matters for publishers on modern Compose apps. | Bump `kotlin = "1.8.0"` in `libs.versions.toml` to a current LTS-ish Kotlin (align with AGP 8.9 compatibility docs), drop the explicit `kotlin-bom` force unless a specific conflict requires it, and document the SDK's minimum-required versions of its transitive deps (OkHttp, Gson, coroutines) in the README so integrators can pre-empt conflicts. | Medium |

## Summary of highest-priority items

The four issues most worth fixing before the next release, given the "must never crash the publisher's app" and adtech-compliance context:

1. **Consent flag has no effect on data collection** (Security, Critical) — the SDK collects Advertising ID, device fingerprint, and IP regardless of `updateConsentStatus(false)`.
2. **`adSize!!` NPE crashes the host app** when a publisher forgets `setAdDimension()` (Crash surface, Critical).
3. **Unstructured coroutines with no exception handling** can crash the host app on any unexpected exception during ad load, click tracking, or `logEvent` (Crash surface, Critical).
4. **`logEvent()` silently drops all data** — a shipped, callable public API that does nothing (Performance/data loss, Critical).
